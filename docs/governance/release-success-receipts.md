# 发布包清理的成功运行依据

业务判断：同一数据库迁移清单和完整包哈希，只证明包内容可核验；文件修改时间不能证明这个版本曾成功运行。清理须保留当前包，以及两个真实成功发布、结构相同、完整包仍存在的旧版本。缺少任一依据时保留全部候选并报告缺口，不制造版本凑数。

OneID 不涉及：只处理发布控制元数据，没有客户或外部身份。持久化是 root 所有的本机发布收据，与既有安装器共用 fd 9 锁；不写业务数据库，不新增队列、Provider 写入或 External Effects。

## 验收合同

- 安装器完成迁移、API、effects Worker、语义 bootstrap 和定时器启动后，调用包内固定的 `record-release-success.py`。它重新读取实际迁移账本，验证 `/readyz` 的 ready 状态与 SHA，以及两个 systemd MainPID 对应 `/proc/PID/exe` 的路径、inode、真实程序哈希和观察期间 PID 稳定性。
- 收据绑定 release SHA、manifest 哈希、完整登记文件集合摘要、程序哈希、实际 schema digest、成功时间、单调成功序号和可选 CI run number。程序只接受 SHA/run number，不接受 passed、人工成功 JSON 或历史包补证参数。
- `/opt/aicrm/release-success` 为 root:root 0700，收据为 root:root 0600 单链接常规文件。先持久化包含原值和候选值的固定 pending 日志，再原子发布并 fsync，最后清 pending。已有历史收据必须全部合法；损坏不重置序号。最小收据、撤销依据和已使用序号永久保留，包回收不删收据。
- 清理器验证固定目录、root 所有权、权限、链接、字段、包当前哈希和结构绑定。只按成功序号选两个不同的旧版本；当前包不计入回滚数量。mtime、任意路径 JSON、缺失收据和被修改的包不能补足数量。实际删除仍重新核验引用、当前包与数据库结构。
- 安装步骤或成功核验失败，安装器回滚，不推进成功序号标记、不执行清理。已有记录只表明过去那次真实观察；不能证明当前运行或新数据库兼容性。
- 发布中断或目录 fsync 不确定时，pending 让清理全部拒绝。固定 `--revoke-incomplete` 只处理该日志：重新核对原包及原值/候选值绑定，持久保存最小撤销依据和序号，再恢复原有效收据或删除新 claim，最后清 pending。新安装器在修改环境和服务前调用，不要求启动失败版本；第三方改写、损坏或无法补偿时继续阻断，不升级成成功。该模式不接受路径或 JSON。
- 提交点是 canonical 收据的文件及其目录 fsync 成功；此前异常走撤销，此后不再将真实持久成功误报为失败或触发安装回滚。提交后的 pending unlink/fsync 是 guard 清理：失败返回已提交并报告待处理；guard 尚在则清理拒绝，guard 已消失则收据合法。崩溃使已删除 guard 再出现只会保守阻断，不会产生错误成功。
- Observer 导入固定辅助脚本前先检查 root 所有权、常规单链接文件与禁止其他用户写入。所有生产 Python 导入入口自行禁止字节码缓存，防止在封存发布包内制造未登记文件；不依赖 CI 环境变量。

信任边界是 root 发布控制面：应用用户不能创建有效收据，应用数据和普通日志不能成为凭证。本合同不防恶意 root 自己改写全部发布控制文件，也不把收据称作外部密码学签名。

## 现有历史包与后续兼容证明

没有本机制收据的旧包继续保留并明确报告缺口。迁移清单不同的旧包即使曾运行成功，也不能通过本收据成为兼容回滚；跨 schema 验证需要独立审查的 Linux/PG 真实回滚旅程及受信证据合同，不能将 readiness-only 或重新编译源码当作原包证明。

参考 GitHub 的 [artifact attestation 验证合同](https://cli.github.com/manual/gh_attestation_verify)：证据必须同时核验内容摘要与产生证据的主体。未来跨环境证据应绑定受审 workflow 与目标数据库结构；本次仅修复本机成功发布证据缺失，不引入该扩展。
