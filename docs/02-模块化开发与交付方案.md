# AI-CRM v3 模块化开发与交付方案

> 文档状态：执行版  
> 适用仓库：`AI-CRM-v3`  
> 前置文档：`01-PRD-迁移范围与新仓库基线.md`

## 1. 开发总原则

v3 的开发单位不是“搬一个目录”，而是“关闭一个用户可观察能力”。每项能力必须同时完成业务语义、数据、权限、API、观测、失败路径和切流边界。

团队默认遵守以下原则：

1. **Journey first**：先写用户旅程和失败场景，再实现包。
2. **One path**：同一业务动作只有一个正式 Service 和一个写入 Owner。
3. **Ports at boundaries**：跨域只使用 Port、Value Object 或领域事件。
4. **No hidden effects**：任何外部效果都必须显式入队、留回执、可对账。
5. **No donor dependency**：旧仓是参考材料，不是库依赖、子模块或远程运行依赖。
6. **Cut over by capability**：一项能力验收后切路由，不等待所有模块完成。
7. **Delete choices early**：不保留“以后可能用”的 legacy 入口、万能 DTO 或第二实现。

```text

├── store/        # 本域表的 PostgreSQL 实现

├── http/         # HTTP DTO 和 Handler
├── worker/       # Durable Job Adapter
└── module.go     # 向 Composition Root 暴露注册入口
```

不是每个领域都必须有全部目录；没有真实职责的目录不创建。

## 3. 强制依赖方向

```text
HTTP / Worker / Provider Adapter
              ↓
             App
              ↓
     Domain + Own Ports
              ↓
          Own Store
```

跨域规则：

- `identity/app` 可以依赖 `customer/port`，不能依赖 `customer/store`。
- `payment/app` 可以依赖 `order/port`、`identity/port`，不能查询它们的表。
- `sidebar/app` 是聚合层，只依赖各域只读 Port，不拥有 Customer、Order、Survey 数据。
- `outbound` 是所有企微写调用的唯一业务 Owner；其他域只能提交发送意图。
- `wecom` 拥有企微读、OAuth、回调协议；不拥有客户画像、订单或标签业务状态。
- `ai` 只产出内容/建议；不选择收件人、不调 Provider、不更新发送终态。
- `platform` 只提供基础设施，不得反向 import 业务域。

机械门禁必须拒绝：

- 跨域导入 `app/store/http/worker/provider`；
- 业务域直接使用其他域表名；
- `os.Getenv` 散落在 config 之外；
- Provider URL 出现在 app/domain/store；
- 手写 generated 目录；
- 运行时代码 import `cmd/migrate-*` 或 `internal/compat` 的具体实现。

## 4. 模块生命周期

每个模块在 `modules/registry.yaml` 中只有以下状态：

| 状态 | 含义 |
|---|---|
| `planned` | 范围已列出，尚未冻结行为 |
| `contracted` | Port、数据所有权、Journey、错误和迁移规则已冻结 |
| `implemented` | 本地实现和测试完成，尚未接真实流量 |
| `shadow` | 读取或事件在生产旁路比较，不拥有写入 |
| `cutover` | v3 已成为唯一写入者和正式路由 |
| `retired-source` | 旧系统相应写入口和兼容层已关闭 |

模块状态不能因“目录存在”“HTTP 200”或“Mock 测试通过”自动前进。

## 5. 模块规格模板

开发任何模块前，必须在 PR 描述或模块文档中填写：

```yaml
module: identity
owner: crm-core
status: contracted
source_baselines:
  - AI-CRM-production@<sha>
  - AI-CRM-v2@<sha>
responsibilities:
  - scoped external identities
  - verified identity provisioning
non_responsibilities:
  - customer profile
  - staff authorization
inputs:
  - IDRef
outputs:
  - ResolveResult
owned_tables:
  - customer_identities
  - identity_conflicts
consumed_ports:
  - customer.CreateForVerifiedIdentity
published_ports:
  - identity.Resolve
  - identity.Provision
published_events:
  - identity.bound.v1
  - identity.conflict.v1
external_effects: none
idempotency:
  key: provider/kind/scope/value
permissions:
  - internal_verified_adapter_only
failure_semantics:
  conflict: fail_closed
journeys:
  - GJ-01
migration:
  source_of_truth_before_cutover: AI-CRM-production
  source_of_truth_after_cutover: AI-CRM-v3
```

没有 `non_responsibilities`、`owned_tables`、`idempotency` 和 `failure_semantics` 的模块不得进入实现。

## 6. 核心模块开发顺序

### 6.1 Platform Kernel

职责：配置、Secret、UoW、PostgreSQL、幂等、审计、Outbox、Job、HTTP 错误、日志、指标、健康、发布版本。

非职责：任何客户、身份、支付或企微业务规则。

完成门：

- 真库事务和嵌套规则；
- 业务事实与 Outbox 原子性；
- 幂等重放和 payload mismatch；
- Job 重试/取消/未知结果；
- PII/Secret 日志扫描；
- health 与 readiness 分离。

### 6.2 Customer

首期只包含最小客户根：`CustomerID`、状态、创建、合并别名/血缘。

后续再增加：姓名、阶段、负责人、标签、画像、时间线。后续能力仍属于 Customer/Contact 子域，但不得让首期 Identity 被完整 CRM Profile 阻塞。

发布 Port：

- `CreateForVerifiedIdentity`
- `ResolveEffectiveRoot`
- `ReadMinimalCustomer`
- `CreateMergeCandidate` 或 Merge 协作 Port

### 6.3 Identity

子模块：

1. `reference`：Kind/Scope/Assurance/Source/Normalizer；
2. `resolution`：只读解析；
3. `provision`：verified 身份建客；
4. `binding`：显式绑定；
5. `conflict`：冲突记录和人工处置；
6. `merge`：版本化策略、CAS、血缘和别名；
7. `migration`：旧身份映射，不进入运行时服务。

第一批不实现自动破坏性合并。先保证任何冲突都可见、可复现、零猜测。

### 6.4 Access

把访问主体分为：

- `AdminPrincipal`：后台管理员/运营；
- `StaffPrincipal`：企微员工；
- `CustomerPrincipal`：公众号/小程序用户；
- `ServicePrincipal`：内部任务/可信集成；
- `CustomerContext`：某个已认证主体在当前会话内访问特定 Customer 的临时授权。

Session、Capability、数据范围、CSRF、OAuth state 和 Customer Context 不能合并成一个万能 Token。

### 6.5 WeCom

子状态机：

| 状态机 | 输入 | 输出 | 禁止行为 |
|---|---|---|---|
| Desktop SSO | 桌面登录 code | Staff Session | 解析外部联系人 |
| Sidebar Staff OAuth | 成员 OAuth code | Staff Session | 建客、读取画像 |
| JSSDK Config | 当前页面 URL | config + agentConfig 签名 | 接受客户端拼接 URL |
| External Contact Context | verified JSSDK result | external_userid fact | 直接写 Customer 表 |
| Callback Ingest | 验签解密事件 | verified provider fact | 持事务做网络调用 |
| Directory Read | Provider token | 员工/群/标签事实 | 直接成为 CRM 负责人/标签状态 |

WeCom 只产出 verified provider fact，再调用 Identity/Customer/Channel Port。

### 6.6 Order

职责：订单编号、Customer、Payer Identity 引用、商品快照、金额/币种、生命周期、结算事实。

不负责：签名、Provider 调用、客户身份推断、商品当前价格、权益具体实现。

订单创建时冻结价格和描述，支付时不得重新读取可变商品价格。

### 6.7 Payment

领域对象：

- `PaymentAttempt`
- `ProviderRequest`
- `ProviderReceipt`
- `PaymentCallback`
- `Refund`
- `ReconciliationCase`

统一状态层级：

```text
accepted → queued → attempted → executed
                         └→ outcome_unknown → reconciled
```

“HTTP 请求成功”“任务入队”“Provider 接受”不能等价为支付/退款最终成功。

### 6.8 CRM Core

依次开发：Customer Profile、Staff Directory、Tag、Stage/Timeline、Channel、Sidebar。

Sidebar 每个标签页都是对领域 Port 的读取或 Command，不允许成为第二套业务 Service。

### 6.9 Content & Commerce

依赖顺序：

```text
Media → Product → Order/Payment
Survey → Identity/Customer
Radar → Media/Identity/Customer
Coupon → Product/Order/Customer
ServicePeriod → Product/Order/Payment/Customer
```

公开页面必须建立独立 Customer/Public Session 边界，不能复用后台 Session。

### 6.10 Operations

依赖顺序：

```text
Segment → Campaign → Outbound
              ↑          ↑
         GroupOps    Automation
```

- Segment 只定义和计算人群。
- Campaign 冻结发送计划、成员和审核。
- Automation 根据事件生成动作意图。
- GroupOps 管理群运营计划和本地状态。
- Outbound 统一完成目标解析、发送排队、Provider 调用和回执。

### 6.11 AI / Stats / Ops / Gateway

- AI：生成、审核、版本，不执行外部效果。
- Stats：拥有聚合表，不直查全部业务表进行在线重计算。
- Ops：只通过健康/Job/Audit Port 管理运行状态。
- Gateway：认证、限流、映射和调用公开 Port，不承载业务规则。

## 7. 单项能力开发流程

### Step 1：冻结供体事实

建立一页 Behavior Contract：

- 用户入口；
- 前置权限；
- 正常输入/输出；
- 空态；
- 边界和错误；
- 幂等/重放；
- 数据变化；
- 外部效果；
- 生产中确实存在的例外。

供体代码只用来举证，不直接决定 v3 包结构。

### Step 2：定义黄金 Journey

先写黑盒 Journey 名称和阶段，例如：

```text
sidebar.first-entry
sidebar.repeat-entry
payment.prepay-callback
payment.callback-replay
payment.refund-unknown-reconcile
```

每个阶段有固定结果和错误分类。

### Step 3：冻结模块合同

明确 Port、DTO、表 Owner、事件、权限、幂等键、Provider 边界、迁移 Source of Truth。

### Step 4：实现 Domain

只写纯状态机和业务不变量；不用数据库、HTTP、环境变量、时间全局值或网络客户端。

### Step 5：实现 App + UoW

应用服务完成用例编排：验证 → 加锁/读取 → 状态转换 → Store → Audit/Outbox → 提交。

### Step 6：实现 Store 和 Migration

- 先写 Migration 与约束；
- sqlc/生成查询；
- 真实 PostgreSQL 测试；
- 索引计划和并发测试；
- Down 不安全时明确 forward-only，不能伪造可逆。

### Step 7：实现 Adapter

HTTP、Worker、Provider 分别实现；Adapter 只做协议、鉴权、DTO 映射和错误转换。

### Step 8：接 UI

UI 只调用生成客户端；未实现能力明确不可用，不回退 Mock，不展示假成功。

### Step 9：Shadow 与对账

对旧系统结果进行只读比较。所有差异进入分类：预期差异、供体缺陷、v3 缺陷、数据隔离。

### Step 10：切流与退役

关闭旧写入口 → 切路由 → 观察 → 完成 Source Retired Gate → 删除临时兼容 Adapter。

## 8. PR 切片规则

一个 PR 交付一个连贯能力，例如：

- “verified external_userid 首次建客并幂等重放”；
- “侧边栏员工 OAuth 只建立 Staff Session”；
- “微信支付回调重复投递只结算一次”。

不接受以下 PR：

- “搬 Identity 模块”；
- “复制 production 基础设施”；
- “先把所有接口放进来以后再修”；
- “只更新迁移矩阵，没有可运行行为”；
- “通过返回空数组兼容旧页面”。

一个能力 PR 可以同时修改 Domain、Port、Migration、Store、HTTP、UI、测试和小量文档，因为这些共同构成一个闭环；但不得顺带重构无关领域。

PR 描述固定回答：

1. 用户可观察变化；
2. 业务和安全不变量；
3. 数据 Owner 与 Migration；
4. 正常/边界/错误/重放测试；
5. 外部效果是否执行；
6. 切流与回退边界；
7. 供体 SHA 和未搬内容。

## 9. 测试与 CI 门禁

### 9.1 测试层级

| 层级 | 验证内容 | 是否阻断相关 PR |
|---|---|---|
| Domain Unit | 状态机、值对象、纯规则 | 是 |
| App Unit | UoW 编排、Port 交互、失败回滚 | 是 |
| PostgreSQL Integration | 约束、锁、并发、幂等、索引 | 是 |
| HTTP Contract | 鉴权、DTO、状态码、错误 envelope | 是 |
| Journey | 完整用户路径和阶段分类 | 核心路径必须 |
| Edge Contract | 反向代理、缓存、no-store、回调路径 | 涉及路由必须 |
| Migration | fresh/up、历史形态、对账、forward-fix | 涉及数据必须 |
| Provider Fake/Sandbox | 签名、验签、超时、拒绝、未知结果 | 涉及 Provider 必须 |
| Production Manual Gate | 真实企微/支付效果 | 仅显式授权后 |

### 9.2 永久关键链路

以下 Journey 在任何相关路径变更时都要运行，不能只放到每日 Nightly：

- `sidebar.first-entry`
- `sidebar.repeat-entry`
- `sidebar.staff-session-expired`
- `identity.concurrent-provision`
- `identity.scope-isolation`
- `payment.prepay-callback`
- `payment.callback-replay`
- `payment.refund-unknown-reconcile`
- `release.edge-routing`

### 9.3 失败注入

每个外部效果能力至少覆盖：

- 连接前失败；
- 请求已发送但响应丢失；
- Provider 明确拒绝；
- Provider 返回目标不匹配；
- 回调重复、乱序、过期、签名错误；
- DB 提交失败；
- Job 重试时幂等键相同；
- 对账结果与本地状态冲突。

## 10. API 与错误规范

统一错误最少包含：

```json
{
  "code": "DEPENDENCY_UNAVAILABLE",
  "stage": "wecom.oauth_exchange",
  "request_id": "...",
  "retryable": true
}
```

规则：

- 对外不返回 Provider Secret、OAuth code、Token、原始身份或上游错误文本。
- 内部日志使用固定 stage 和安全数值错误码。
- 409 用于幂等载荷漂移、CAS 冲突、身份冲突等可确定冲突。
- 422 用于合法 JSON 但业务语义不支持。
- 503 只表示当前依赖不可用，必须携带安全 stage。
- 任何支付/外部效果 API 都不得用 200/202 暗示最终执行成功。

## 11. 数据与事件规范

### 11.1 表命名和所有权

每张表在 `modules/registry.yaml` 或 ownership 清单中登记。跨域外键可以存在，但写入只能由 Owner Service 完成。

### 11.2 Event Envelope

```json
{
  "event_id": "uuid",
  "type": "identity.bound.v1",
  "aggregate_type": "customer",
  "aggregate_id": "123",
  "occurred_at": "...",
  "idempotency_key": "...",
  "payload": {}
}
```

事件 Payload 只放下游需要的最小信息；外部身份和 PII 默认不进入通用事件。

### 11.3 版本和兼容

- Event、API 和 Job payload 都显式版本化。
- 新字段优先可选；删除/改义必须新版本。
- 临时兼容层有删除 Gate，不允许永久吞掉未知字段。

## 12. 外部效果规范

Provider Adapter 返回统一结果：

```text
not_attempted
attempted
accepted
rejected
outcome_unknown
```

应用层只根据明确证据推进状态。`outcome_unknown` 的后续动作只有：

- 使用原幂等键查询；
- 等待可信回调；
- 人工提供证据后对账；
- 由 Provider 明确允许的幂等重试。

禁止：换新键盲重试、把超时标记成功、仅凭任务结束推断 Provider 完成。

## 14. Definition of Ready

能力进入开发前必须具备：

- 供体 SHA 与行为证据；
- 用户 Journey 和错误路径；
- 数据 Owner；
- 权限模型；
- 幂等策略；
- 外部效果分类；
- 迁移 Source of Truth；
- 切流和回退边界；
- 明确“不搬什么”。

任何一项缺失时，先完成合同，不直接复制代码。

## 15. Definition of Done

能力完成必须同时满足：

1. Domain/App/Store/Adapter 边界通过机械检查；
2. 正常、边界、错误、重放测试通过；
3. 真库和 Edge 测试按范围通过；
4. API/Event/Job Schema 已版本化；
5. 日志无 PII/Secret；
6. Provider 结果没有被夸大；
7. 数据迁移和对账完成；
8. v3 是唯一写入者；
9. 正式路由已切或明确仍处于 shadow；
10. 旧入口有退役任务和 Owner；
11. Dashboard 和告警可定位阶段；
12. PR 记录供体、差异和回退方案。

## 16. 开发效率指标

每个阶段持续跟踪：

- PR 从首个提交到 merge-gate 的 P50/P90；
- 首次 CI 通过率；
- 一个能力涉及的领域数量和 Composition Root 变更量；
- 关键 Journey 失败数；
- 上线后逃逸缺陷、回滚和 hotfix 数；
- Shadow 对账差异及平均关闭时间；
- 临时兼容层存量和超期数量；
- Provider `outcome_unknown` 未对账数量；
- 旧系统仍拥有写权限的领域数量。

优化目标是减少跨域选择和返工，不以提交行数或搬迁目录数衡量进度。

## 17. 首批执行顺序

新仓库创建后，严格按以下门顺序推进：

```text
Repository Baseline
→ Platform Kernel
→ Minimal Customer
→ Identity Ref/Resolve/Provision
→ Access Session
→ WeCom Staff OAuth + JSSDK Context
→ GJ-01/GJ-02
→ Order + PaymentAttempt
→ WeChat Pay Callback/Reconciliation
→ GJ-04/GJ-05
→ CRM Core Modules
```

在 GJ-01/GJ-02 通过前，不开始搬完整 Sidebar 页面；在 GJ-04/GJ-05 通过前，不开始搬公开购买、优惠券和周期权益。这样每一层都建立在已验证的基础事实之上，而不是继续用页面驱动底层补洞。
