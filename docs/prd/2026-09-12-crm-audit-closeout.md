## 1. 目标与业务判断

本次交付关闭迁移后仍未人工确认的缺陷、契约遗漏和 UI 不一致问题，并为每个能力建立可独立追踪的验收证据。最终交付必须同时回答六个问题：代码是否进入正确的 PR、CI 是否通过、PR 是否合并、线上是否运行对应 SHA、浏览器业务路径是否可用、外部 Provider 是否产生了可核对的结果。

本 PRD 不把页面可打开、HTTP 200、任务已排队、进程健康或配置存在当作业务完成。历史迁移数据保持原事实；无法由可信证据确认的身份、归属、支付或外部效果继续停留在待核验状态，不通过猜测、隐式建客、自动合并或重放未知效果清零台账。

真实外部验收使用用户批准的内部白名单：测试员工、测试客户和测试群均已指定，但具体标识只保存在受保护的会话验收记录中，不写入本公共文档。支付与退款只允许测试订单，单笔支付上限 0.01 元，本轮累计上限 0.10 元，允许对本轮测试订单执行全额退款；任何超出白名单或额度的操作都不在本 PRD 授权范围内。

## 2. 架构边界

### OneID

客户 360、客户归属、HXC 身份、客服/群成员关联和迁移核验涉及 OneID。实现必须继续使用 `internal/identity/port` 与 `customers.id`，保留 kind、scope、value、assurance、source；没有唯一可信证据时保持 pending 或 conflict。任何修复不得新增身份匹配器、隐式建客或破坏性自动合并。

Radar、运营闭环配置、UI 组件、OpenAPI 文档和 readiness 诊断本身不涉及 OneID，不因统一格式而引入客户主键。

### Persistence 与 External Effects

- Radar 统计、客户 360 风险降级、负责人展示、分页和 readiness 读取沿用各自领域 Store 与只读 Port；不得跨领域读取表。
- 素材刷新和运营闭环批次读取属于现有持久化任务/读模型，复用 `platform/jobqueue` 及已有事务边界，不新增领域队列、Worker、重试或对账状态机。
- 企微发送、客服/群变更、支付和退款仍由现有 `outbound`/`externaleffects`/`payment` 边界负责。业务域只提交不可变意图，使用稳定幂等键和原有收据、重放、对账与 `outcome_unknown` 语义；不得因验收换新幂等键重试。
- 本文档、UI 修复和 OpenAPI 补齐不产生 Provider 写入。

UI 统一沿用现有标准组件和业务语义，做窄范围整改，不扩展为全站重设计。桌面、780px 窄屏和手机宽度均必须检查加载、空态、失败、筛选、弹窗、按钮层级、状态标签和分页。

| ID | 问题 | 完成标准 |
|---|---|---|
| UI-01 | 运营闭环上传、历史批次和主操作层级不一致，窄屏布局声明失效 | 统一标准按钮、表单、历史选择和反馈状态；修复移动端网格布局；保留“标题来自 Excel、空标题失败、每批必须有统一封面、提交后冻结快照”的既有合同 |

### 迁移和人工验收

以下项目是独立门，不因代码修复、数据库计数或总入口健康而自动关闭：

1. 客户同步：核对发现、绑定、投影、冲突和失败计数，并确认 API/UI 读回。
2. 身份与 scope：继续核验无法取得独立来源证明的历史身份；保留 pending/conflict。
3. HXC：核对 OneID/UnionID/手机号/双键的匹配、未匹配和冲突集合；不得按近似值绑定。
4. 问卷：核对定义、题目、选项、提交、解密答案、推送历史和 SCRM 历史；提交推送需区分 Provider accepted、executed 和用户回执。
5. 自动化与 AI：核对审批、内部任务、External Effects、Provider 结果和客户回执；排队不等于发送。
6. 运营闭环与群运营：核对计划、批次、封面、负责人、成员、审批、冻结历史和实际发送链路。
7. 商品、订单、会员、优惠券、支付和退款：逐条核对金额、期限、受益人、状态、退款幂等和原始证据。真实支付严格受本 PRD 第 1 节的白名单与额度限制。
8. 媒资、侧边栏、归属转移和消息存档：核对读回、旧链接、权限、目录事实和外部回执；未知效果不重放。
9. 标签、配置和 Open Platform：核对定义/权限/作用域和实际 Provider 回读；配置存在不等于写入成功。

## 4. 实施与审查顺序

每个用户可观察缺陷或能力单独形成 PR，依赖关系清楚后再合并：

1. 先合并 CI 部署开关控制的独立 PR；默认保持 CI 检查，生产 deploy 必须显式 opt-in。
2. 实施数据展示和状态安全项（AUD-01 至 AUD-04）。
3. 实施分页、刷新计数和 readiness（AUD-05 至 AUD-07）。
4. 补齐 OpenAPI 与 dispatcher 契约（AUD-08）。
5. 先修公共选择器和布局基础，再接入运营闭环、GroupOps、渠道页面（UI-01 至 UI-06）。
6. 逐项执行迁移人工验收和真实白名单 Provider 验收。
7. 由总控审查每个 PR 的业务判断、OneID/持久化/外部效果边界、测试证据和发布清单，再进入 GitHub 合并。

执行角色遵循项目约定：luna max 负责基础核验、审计和回归；terra high/xhigh 负责标准开发和核心修复；只有遇到常规审查无法解决的复杂问题才引入 sol。任何发现身份错误归属、重复支付/退款/企微效果、鉴权绕过、跨域表写入或迁移静默丢失时立即停止相关实现并升级。

## 5. 测试和证据

- 后端缺陷必须有对应失败场景：统计不可用、订单依赖失败、归档启用、计划超过 100 条、跨页恢复重复、缺失迁移结构。
- 前端必须用实际发布 CSS/Host 验证桌面、780px 和手机宽度；重点页面不得整页横向溢出，选择器单选/多选和客服姓名必须从真实目录事实断言。
- 每个 PR 运行适用的 Go、race、vet、架构、OpenAPI、前端 Host/DOM、浏览器旅程和 PostgreSQL 集成检查。没有测试数据库时的跳过只能记录为未验证，不能写成通过。
- 真实 Provider 验收单独记录请求意图、Provider 接受、执行结果、回执/对账和失败阶段；测试订单必须核对全额退款，不能以支付接口返回成功代替退款结果。
- PR、CI、merge、deploy、browser、provider 六类证据分别登记在 [验收台账](../assessments/2026-09-12-crm-audit-closeout/acceptance-ledger.md)；一类证据通过不自动替代其他五类。

## 6. GitHub 合并与本地 SSH 发布

GitHub 只负责版本、审查和 CI。当前基线的 `.github/workflows/ci.yml` 在 `main` push 且 `check` 成功后会进入 deploy；workflow dispatch 只有明确指向 `main` 且 `check` 成功才会 deploy。当前工作流没有通用的“合并但跳过 deploy”输入，因此必须先合并独立的 deploy opt-in 控制 PR，并由其默认值保证普通合并不上传生产。不得直接修改生产配置或关闭检查来绕过门禁。

最终发布流程：

1. 从最新 `main` 的准确合并 SHA 构建 Linux 目标架构的完整发布包，校验包内容和 SHA-256。
2. 先验证无其他发布正在安装或切换，再通过本机已有 SSH 配置上传；只读取 SSH 用户和目标，不读取、复制或输出私钥、Secret 环境变量和受保护配置正文。
3. 调用版本匹配的安装程序，执行 forward-only migration、服务切换、回滚保护和 `/healthz`/`/readyz` 校验。
4. 核对线上 SHA、正式 HTTPS、登录后关键页面和接口，再执行受控真实 Provider 验收。
5. 发布成功、浏览器验收和 Provider/回执验收分别记录；上传完成或进程健康不能单独宣布业务完成。

安装包必须包含当前 release 所需的二进制、迁移、前端产物、服务单元和部署脚本；不得把 macOS 二进制或本地临时测试产物上传到服务器。数据库迁移只前进，不用破坏性回滚掩盖失败。

## 7. 不在本次范围内

不新增业务模块、不重做旧系统、不恢复已退休路由、不迁移旧发送队列、不自动合并身份、不重放未知支付/退款/企微效果，不把旧 PR 的冲突分支逐个搬入 main。旧系统仅作为行为证据和必要叶子协议参考，v3 仍是唯一新能力主线。
