# 群运营基础配置保存可靠性

## 业务判断

运营人员在草稿或停用计划的“基础配置”页可能快速双击“保存基础配置”或“保存当前维度”。这两个入口目前共用 `savePlan`，却各自发出 PUT：首个请求可以成功，第二个请求因旧版本返回 409，而页面只显示“已保存”。计划名称留空时，页面又会静默用旧名称回填并提交，用户无法判断输入是否真的被接受。

保存应表示：一次明确提交只写一次，成功后以服务端回读的计划为准；失败必须显示原因、保留未提交输入，并允许用户修正后再次提交。计划 #14 是用户的专用草稿验证对象，本修复不读写它；测试使用隔离 fixture。

## 范围

1. 仅在 V3-owned `web/v3/groupOpsStandard.js` 的共享 `savePlan` 增加单次 in-flight 锁，覆盖“保存基础配置”和“保存当前维度”。
2. 保存开始后禁用两个入口并显示处理中；等待 PUT 与权威 detail 回读都完成后才显示“已保存”。
3. 失败显示可理解的错误，保留当前表单输入；不自动补写、不自动重试。
4. 显式 `trim` 计划名称；空名称在浏览器端拒绝并提示，绝不以 `|| state.plan.plan_name` 静默回填。
5. 保留现有 revision / If-Match / Idempotency-Key / CAS 服务端兜底与既有 action feedback adapter；不修改冻结 controller，不新增平行状态机、队列或 API。

## 不在范围内

- 不更改计划、绑定群、节点、Webhook 或外部消息执行语义。
- 不启用、归档、删除或修改线上计划 #14，也不触发 Provider。
- 不改后端 CAS、持久化模型、迁移或外部效果流程。

## 分类与复用

- OneID：不涉及。本次仅提交既有计划的本地配置，不解析或关联客户身份。
- 持久化：涉及既有 Group Ops 计划版本写入；复用当前 PostgreSQL Unit of Work、审计/收据和 CAS，不改变事务边界。
- External Effects：不涉及。基础配置保存不创建 Provider 写入、outbound intent 或任务。
- 前端：复用现有标准 Group Ops action / feedback seam；不改 frozen controller。GitHub #212 已确立“保存失败可见、输入保留、保留版本校验与幂等”的同域契约。

## 验收

| 场景 | 期望结果 |
| --- | --- |
| 单次成功 | 仅一个 PUT，随后完成 detail 回读，才显示“已保存”。 |
| 连续双击 / 两个保存入口 | 整个 in-flight 生命周期只允许一个 PUT。 |
| 409 | 显示冲突，保留输入；不伪造成功。 |
| 500 / 网络失败 | 显示失败，保留输入；不自动重试。 |
| detail 回读失败 | 明确显示“已保存但回读失败”，锁保持到只读恢复成功；不允许盲目再发 PUT，并保留输入。 |
| 空白计划名称 | 本地拒绝，零 PUT。 |
| 失败后重试 | 修正输入后可使用同一入口重新提交；仍一点击一写。 |
