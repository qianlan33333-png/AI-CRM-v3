# 新 CRM 开发前置流程与上线验收标准

## 适用范围与分类

适用于新功能、能力扩展、Bug 修复、调试、并行开发、合并和上线。本文自身：

```text
OneID：不涉及
Persistence：stateless
External Effects：不涉及
```

业务代码仍执行 `skills/aicrm-v3-development/SKILL.md` 的三轴分类。

## 新功能三步门禁

1. 市场/GitHub 调研：至少 2 个成熟方案和 1 个高质量 GitHub 参考；找不到时记录搜索范围、关键词、时间和结论。
2. 复用评估：检查已有领域、共享组件、标准组件、OneID、持久化、内部任务和 External Effects，记录采用、扩展、舍弃和新增理由。
3. 完整 PRD：包含用户、业务判断、成功标准、接口/数据/权限边界、架构分类、测试、上线、监控、回滚和并行依赖。

PRD 经用户确认后冻结；重大范围、合同或风险变化必须重新确认。

## 一次闭环交付

所有假设、PRD、复用方案和风险边界确认且用户明确开始开发后，执行者持续推进到完整上线验收，不把可由既定流程判断的常规选择逐步退回用户。只有新的业务决策、红线风险、凭据/权限缺失或部署证据不一致才暂停并报告。

完整终点为：实现 → 预发布机 `49.232.57.128` 按板块编译并安装 → 预发布专项验收 → GitHub 轻量一致性门禁与合并 → 预发布机将同一已验收包串行推送到生产 → 部署后认证读回 → 观察窗口验收 → 触发一次“彩纸礼炮”庆祝。没有业务需要时不再重复本地全量上传；本地只做快速反馈和发布脚本自检。

彩纸礼炮规则：只有版本、健康状态、认证读回、真实业务读回和观察窗口全部通过后，才调用 Codex 的 `mcp__codex_app__fire_confetti` 一次。构建成功、PR 合并、部署开始、服务启动或仅 `/readyz` 通过都不能触发；部署失败、回滚、结果未知或观察窗口未结束时不得触发。同一上线事件只触发一次，重复重试不得重复庆祝。

预发布使用与生产一致的系统、PostgreSQL 16、systemd 和发布目录，使用合成 CRM 数据完成迁移、健康、关键 API、真实 Chromium 旅程和回滚验收；不复制生产敏感数据。预发布成功后生成 SHA/tree 绑定 receipt。

GitHub PR 默认只检查当前 head/tree、最新 main、冲突、治理、secret scan、迁移编号和证据字段；运行时代码、迁移、发布包或前端页面变更还必须核对与当前 tree 绑定的预发布 receipt。纯 CI、治理、Skill 和文档变更不要求无意义的应用部署 receipt，也不重复本地长测试。完整云端 CI 仅由维护者通过 `workflow_dispatch` 并明确设置 `force_full=true` 执行。合并若生成新的 merge/squash SHA，必须比较 merge 后 tree 与预发布 tree；tree 不一致就重新预发布。

### 预发布编译与同包晋级

运行时代码只从当前 PR 的准确 commit 在预发布机编译。编译器固定为 Linux amd64，包生成后立即执行 ELF 架构检查、迁移编号与最新 `main` 冲突检查、包清单和 SHA-256 校验；任何一项失败都在上传前停止。预发布安装器再次检查主机和每个可执行文件，避免 `Exec format error` 到迁移服务才暴露。

预发布验收只覆盖本次声明的能力板块及其共享依赖。无关 Provider 未配置、其他板块的外部服务 503 或历史页面告警分类为 `external_config_unavailable`，只有当它属于本次能力的依赖时才阻塞。receipt 必须记录能力板块、commit/tree、包摘要、迁移结果、健康状态和真实业务读回。

合并后不重新在本地编译，也不从另一个 checkout 重新打包。预发布机持有已验收包，在发布锁下把相同包摘要推送生产；生产仅重新读回版本、健康、认证和本次板块的真实业务结果。一次只允许一个生产部署，使用 GitHub environment/concurrency 或等价的主机发布锁排队。

生产部署固定由本地 SSH 登录 `124.220.53.183`。用户提供的 `/Users/qianlan/Downloads/zhengshi.pem` 必须保持 `0600`；私钥不得进入仓库、PR、日志或命令输出。通过 `deploy/run-release-as-root.sh` 在 root shell 内持有 fd 9 锁，禁止直接用 sudo 传递普通用户的锁描述符。部署前严格核对 known_hosts/远端 Host Key；不匹配时立即停止。

## 并行板块与冲突治理

每个工作项登记：

```text
工作项/板块、负责人、分支或 worktree、状态、修改范围、共享入口、依赖项、预计上线窗口
```

Composition、公共组件、迁移、CI、Provider 和部署脚本串行合并；普通领域可并行但必须在合并前同步最新 `main` 并重跑受影响测试。Debug 分支不能直接成为稳定依赖。

合并前填写：

```text
当前 main HEAD/tree：
活跃分支与 PR：
重叠文件/模块/迁移/API：
其他已合并但未部署版本：
当前排队上线版本：
正在执行的部署或观察窗口：
本次合并需要重新运行的测试：
```

存在部署未完成、部署后读回未完成、未知结果、回滚未完成、共享合同顺序依赖或过期 HEAD 时暂停并重新排队。

## 发布队列

已合并且完整验证的提交进入“待上线”；一次只执行一个生产部署。部署后独立验证版本、迁移、健康、管理员页面和真实业务读回；观察窗口无异常后才放行下一版本。CI 可简化编排和重复报告，但不能删除适用测试、真实验收、部署后读回或回滚准备。紧急热修必须由用户明确标注，并记录插队原因、回滚方案和补齐验证。

排队上线不等于已上线，部署成功不等于业务验收完成。

## Bug 修复流程

保存失败证据 → 判断根因和影响 → 先补回归测试/旅程 → 最小根因修复 → 执行原失败阶段和受影响全链路 → 输出防复发措施和未验证项。除非用户明确标注线上热修，否则走完整流程。

## 上线前测试矩阵

预发布必须完成适用层级：静态/架构/敏感信息；板块编译/单元；PostgreSQL 16/迁移/事务；集成/权限/真实读回；前端 typecheck/build/组件合同；受影响的真实 `Test…ChromiumJourney`；OneID scope/verified/pending/conflict；External Effects 幂等/重放/回调/对账；发布包、Host Key、部署后读回、监控和回滚。小范围业务改动不再因无关全仓 lane 阻塞。GitHub 只保留一致性和治理证据门禁。

PR 只保留准确 HEAD/tree、并行与发布快照、测试摘要、证据目录和未验证项。作者声明只作为上下文，不作为独立上线门禁；门禁只保留当前 head/tree、预发布 receipt、治理安全检查和部署后读回。

## 合并标准

分支已同步最新 `main`；并行与发布快照完成；无冲突上线任务、未知部署或未结束观察窗口；本地适用测试和真实业务读回完成；PR 写明 OneID、Persistence、External Effects、前端复用和影响范围；不存在身份错误归属、重复外部效果、跨领域写表、静默丢数据或第二套执行/身份内核。

## 奥卡姆剃刀约束

优先复用已有能力，采用最小接口、最小改动和单一 Owner。新增队列、身份系统、组件体系、重试机制或发布流程，必须先证明现有能力无法满足。

## 国内预发布机发布路径（当前默认）

预发布机 `49.232.57.128` 不承担 GitHub 拉取。开发机在确认干净、准确的 v3 commit 后生成并校验 Git bundle，通过 SSH 上传到预发布机；预发布机在 Linux amd64 上完成编译、包清单和架构检查，再安装并验收受影响板块。`deploy/build-release-on-staging.sh` 默认要求 `AICRM_SOURCE_BUNDLE`，缺失时直接失败，不回退到 GitHub clone。

预发布构建使用 `/opt/aicrm/staging-build.lock` 单飞锁，锁覆盖清理、解包、编译和 receipt 生成，禁止并行任务互相删除构建目录。只有安装、健康检查和真实业务读回完成后，receipt 才能从 `built` 变成 `accepted`。

合并后的 squash commit 可以与预发布构建 commit 不同，但必须与 receipt 具有相同 tree；生产晋级使用 receipt 绑定的构建 commit 和 package SHA，拒绝旧 tree、旧 head 或不同包。GitHub 只核对当前合并 tree、accepted receipt、包摘要和并行发布状态。

### 预发布能力声明与无关 Provider

预发布业务读回必须由能力声明驱动。声明包含 `affected_modules`、`required_routes` 和 `required_provider_dependencies`；验收器只把声明中的路由和 Provider 作为阻塞条件。未声明的 Distribution、支付、群运营或其他 Provider 返回 `503 distribution_unavailable` 时，记录为 `external_config_unavailable`，继续完成当前板块验收；声明了该 Provider 时，同样的 503 必须阻塞。该分类由 `scripts/validate-staging-capability.py` 输出，禁止凭日志文字人工猜测。

验收辅助脚本不生成 accepted receipt，也不执行 HTTP 请求。required_routes 是非空路径字符串数组；observations 必须覆盖全部必需路由/Provider，并记录 status 与业务断言 business_verified。HTTP 200 本身不能替代业务验收。支付板块默认使用 acceptance_mode=virtual：在预发布用本地虚拟支付适配器或确定性数据库事实验证待支付订单重购、幂等、已支付拦截和状态回读，不连接真实支付、不扣款、不等待 Provider 回执。只有明确需要 Provider 集成的板块才使用 acceptance_mode=live。

支付逻辑验收边界：预发布环境是虚拟环境，不配置真实商户支付能力。Payment PR 的能力声明应使用 `acceptance_mode: virtual`，业务读回必须覆盖 pending 订单允许新幂等键创建、旧订单保留、同键重放返回同一订单、已支付商品仍被拦截。receipt 记录虚拟适配器或本地事实证据；这证明业务逻辑完整，不证明真实支付渠道可用。真实扣款、回调和 Provider 对账属于单独的支付渠道验收，不得成为普通支付业务 PR 的默认门禁。

### 预发布外部调度边界（统一规则）

预发布环境默认不连接任何真实外部调度能力，包括支付、企微发送、群发、自动化 Provider、Webhook、分账和其他 External Effects。所有涉及外推的板块使用 `acceptance_mode: virtual`：通过本地虚拟适配器或确定性数据库事实验证意图创建、幂等键、队列接收、重放、状态转换、失败分类和业务读回；外部 503 或未配置统一记录为 `external_config_unavailable`，不阻塞本板块。只有明确授权的渠道联调任务才能使用 `acceptance_mode: live`，并单独记录 Provider 凭据、回调、对账和撤销边界，不作为普通 PR 的默认验收。

## 合并预览候选与单一发布队列

预发布构建对象固定为最新 `main` 与 PR 的 merge preview，而不是 PR 分支 head。候选清单必须保存 `candidate_id`、`pr_number`、`base_main_sha`、`pr_head_sha`、`merge_preview_sha`、`tree_sha`、`package_sha256`、`affected_modules`、`shared_dependencies` 和状态。`main` 前进后旧候选自动失效，必须重新生成并验收；旧 receipt 和旧包只作历史证据。

预发布机是唯一 Linux amd64 构建和大包传输节点。Git bundle 优先排除 `base_main_sha` 生成增量对象包，缺少基线时才回退完整包；每日 GitHub 源码镜像仅作缓存，失败标记 `mirror_stale` 且不阻塞冻结候选。验收完成后由预发布机在严格 Host Key、临时 0600 生产密钥和生产锁下直接把同一包推送正式机，Runner 不下载或中转发布包。

发布队列一次只允许一个候选进入生产相关状态。普通领域按影响范围验收；Composition、迁移、公共组件、Provider、External Effects、部署脚本和 CI 自动进入共享串行队列。生产晋级再次校验 merge tree、package SHA、receipt、迁移和 readiness，任一不一致保留旧版本。
