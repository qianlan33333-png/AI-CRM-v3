## 2. 首要架构分类

本次记录本身不产生业务写入。未来实现按以下分类审查，依据 `skills/aicrm-v3-development/SKILL.md`：

- OneID：涉及外部客户上下文解析、统一客户读取、问卷归属及手机号绑定状态。只通过 Identity Port 解析带作用域的可信身份；Resolve 不隐式建客，不自行按姓名或手机号猜测合并。
- 持久化：档案修改属于所属领域的本地事务；读取通过各领域稳定 Port。需要原子提交的业务状态、审计、幂等和 Outbox 必须在同一 PostgreSQL UoW。
- 外部交互：区分 SDK 配置及读取、客户端当前会话交互、服务端 Provider 写入。先核定旧版所用官方 API 的真实语义。服务端企微写复用 outbound／External Effects，不另造队列，也不擅自用后台群发替代客户端操作。
- 冻结旧版源、测试和接口载荷；沿用当前去重机制登记引用，不再整目录复制出第二份权威源码。

## 3. 必须交付的修复范围

### 3.1 标准版 UI 与完整字段恢复

恢复客户头部、绑定状态、标签呈现、三列多行导航、普通／周期商品与订单切换、列表卡片、价格、日期、详情入口、按钮与间距。支持企微窄窗口，不出现必须横向滚动才能找到主要功能的布局。

核心画像按标准版核查用户来源、行业信息、行业具体描述、需求／卡点／跟进状态及保存行为，不能只留下姓名、公司两个可编辑字段。字段要映射到正确 V3 Owner，不能仅补输入框。

常规界面不堆叠“本地安全投影”“520ms”“client_callback”等实现说明；诊断信息保留在适当位置，业务提示使用用户能理解的语言，同时不得把未知结果写成成功。

验收：相同窗口尺寸逐页对照标准版，验证字段读取、修改、重开后保持和失败反馈。保留用户时间线，按 3.6 去除聊天功能。

### 3.2 进入后自动完成 SDK 初始化及客户识别

用户反馈当前需要再点一次才授权。先确认这个点击属于页面自设启动、员工 OAuth、SDK 配置、应用鉴权还是平台强制交互；分别记录根因。

恢复进入侧边栏后自动初始化、合法已有登录态复用、读取当前客户上下文的流程；不要求用户额外点击页面按钮才能开始正常识别。仅失败时提供重试。切换客户会话后必须更新上下文并清理前一客户缓存。

正式 PRD 固定 SDK 来源、版本、签名 URL、应用身份、授权 API 和初始化顺序，并核对官方机制。不得承诺绕过平台必须的首次同意，不将所有症状预判为 SDK 版本问题。

验收：真实企微环境冷启动、重开、客户切换、失效登录、初始化失败恢复；浏览器协议测试不能代替真实客户端验收。

### 3.3 问卷为空与客户身份／手机号状态核查

同一测试客户标准版有多条答卷，V3 显示 0；标准版显示手机号已绑定，V3 显示未绑定但画像另有脱敏手机号。必须核查而非直接调整显示。

按链路定位：当前 external_userid 与企业作用域 → OneID 解析 → canonical customer → 问卷所属身份与作用域 → 答卷领域读取 Port → 分页／过滤参数 → 页面适配。手机号展示字段与可信绑定身份分别核对，不能因为存在文本手机号就标记为已验证。

将原因明确分为：V3 缺少历史记录、可信身份尚未关联、查询／分页／过滤错误、接口或页面映射错误。缺历史数据不能伪报为 ID 已修复；需要历史导入时单列待办及证据，不把旧库变成正常运行数据源，不在本项中默认执行全量迁移。

验收：用已知归属的测试答卷走通列表、数量、答题时间、题数及答案详情；验证错误作用域、未解析和冲突不会读到其他客户。真实测试客户的历史差异必须给出具体原因及处理结果。

### 3.4 商品发送到当前会话

用户报告点击后只出现 `client_callback`／`delivery_unknown`，商品未进入会话。该现象不能单凭提示文字定因。

追踪标准版实际发送方式、SDK API、权限、当前会话上下文、消息类型、参数、链接、标题、封面及公开购买页。明确标准版动作究竟是填入输入框、发起客户端确认还是立即发送，并按真实标准行为恢复。

JS 回调、进入会话和客户送达是不同证据。若官方 API 不提供外部送达回执，不能把缺少该回执当成操作必然失败，也不能仅修改提示冒充修复。不得自动重复发送或替换为服务端营销消息。

验收：在受控真实客户会话中，点击一次看到正确商品卡片进入标准版对应位置，标题／价格／封面／购买链接正确；覆盖普通和周期商品、取消、SDK 失败、客户切换及重复点击。不向未授权客户试发。

### 3.5 优惠券与素材实际接通

优惠券接现有 V3 领域能力，恢复标准版券列表、优惠金额、适用商品、领取截止、复制领取链接等实际操作。核查有效期、可领取条件和权限，不能只移除灰色禁用样式，不增加标准版没有的自动发券动作。

截图 11 的素材也纳入核查：图片素材／雷达链接、搜索、缩略图、标签和发送。复用已有素材与雷达 Port，确认所发资源可访问、归属正确；标准版自身加载异常不能作为必须复刻的行为。

验收：可用券正常显示、链接可打开并遵循领取规则；不可用券状态准确。素材搜索、预览与会话动作实际通过。

### 3.6 从侧边栏移除聊天记录

移除“其他客服聊天”“聊天活动”及侧边栏内任何聊天记录入口、内容卡片、重试按钮和错误提示；同时停止这些入口触发的后台请求。

只调整侧边栏前端和必要的入口装配。不删除存档后端、数据库、归档任务或其他业务使用的读取能力；不取消主对话的会话存档接通项目。用户时间线保留非聊天活动。

验收：所有导航状态、直达参数和旧选中状态恢复后均不再显示聊天入口；网络检查不再由侧边栏触发聊天记录请求。

### 3.7 订单展示与状态对照

对标标准版订单名称、金额、订单号、状态、时间、详情及普通／周期分类。截图中疑似有“已支付／全额退款”差异，但必须先核定相同订单号，不能仅按商品名判定状态错误。

若为相同记录，追踪退款终态、投影、读取契约与展示映射；若因数据快照或历史缺失，单独说明。不要重新开发支付、退款或权益内核。

## 4. 正式 PRD 前的证据要求

1. 冻结完整可遍历的旧仓提交及 V3 当前提交，列出全部跟踪文件库存；将 CRM 能力映射到页面、路由、命令／服务、接口、测试与依赖。记录读取失败和未覆盖项，不能声称未检查的能力已覆盖。
2. 对本项涉及的侧边栏流程逐项列“原样复用／Go 等价迁移／V3 已有／待补齐”，给出具体源码路径和原测试依据。
3. 对本文症状逐一给出已确认根因或待验证假设，尤其区分 UI、SDK、身份、数据缺失及运行装配问题。
4. 形成正式 PRD：字段映射、领域 Owner、稳定 Port、授权边界、事务、协议、历史数据依赖、逐项验收和回滚方式。
5. 由主对话与正在进行的客户同步、问卷、配置、存档和前端工作协调修改归属，再开始独立板块 PR。本文不触发其他对话或生产操作。

## 5. 开发、上线与验收要求

- 开发前冻结旧行为，先修具体失败，再做相关编译、架构、真实 PostgreSQL 和浏览器／协议检查，最后完整 CI；不弱化断言来消除差异。
- 真实 PostgreSQL 覆盖实际涉及的身份隔离、持久化、事务回滚、并发、幂等；不为纯样式改动制造无关的后台机制。
- 发布包必须包含构建后的前端资源；从干净检出检查侧边栏真实入口、深链资源、缓存更新与后端契约。
- 回滚保留前一前端包及对应应用版本；涉及新增字段时避免破坏性迁移，不能用回滚代码撤销已经产生的外部发送。
- 明确分开记录实现、测试、审核、合并、部署、配置生效、真实企微验收。先前“识别客户已正常”的反馈不能覆盖本次新增的问卷、发送、优惠券及 UI 验收。
