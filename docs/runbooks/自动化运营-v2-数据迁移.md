# 自动化运营 v2 数据迁移 Runbook

## 0. 生产决策：迁移能力语义，不复制旧数据

2026-09-04 对 `crm-prod` 的只读盘点显示：13 张通用数据迁移契约表中只有旧 `segments`，以下 12 张不存在：

1. `ai_audience_package_groups`
2. `ai_audience_package_metadata`
3. `ai_audience_package_configuration_versions`
4. `ai_audience_package_automation_bindings`
5. `ai_audience_package_senders`
6. `segment_members`
7. `identities`
8. `automation_agent_configurations`
9. `automations`
10. `automation_rule_versions`
11. `automation_enrollments`
12. `automation_execution_actions`

这不表示 v3 能力依赖 13 张表，只表示该旧库不符合“整包历史数据导入”的通用源契约。当前产品决策是不导入旧人群、成员、运行或效果，而在 v3 内幂等安装可真实计算的默认语义：

- 分组：`默认运营人群`。
- 人群包：`近7天活跃客户`、`近30天活跃客户`、`近90天活跃客户`。
- 成员只由 Customer 领域稳定 Port 读取，并经 OneID canonical root 解析；不建客、不绑身份、不合并。
- 每日 09:00 Asia/Shanghai（`0 1 * * *` UTC）的刷新策略被写入不可变配置版本，首次快照由 River 持久任务刷新。
- 三个包均保持 `paused`；不创建 Agent、发送人、策略、消息意图或 Provider effect。
- 引导只在配置版本仍为 1 时补齐系统默认；管理员修改或归档后，后续部署不会覆盖。

部署会自动运行 `bootstrap-automation-operations`，并在 journal 输出不含客户标识的数量、摘要、刷新 run ID 和状态。本文下方的历史数据导入流程仅在未来出现符合 13 表契约的独立数据源，且产品再次明确要求复制历史数据时才启用。

## 1. 边界与停止条件

- 供体固定为 `AI-CRM-v2@6bfbe5816bb89913c70adaca87d6a486260e016e`，源凭据必须是只读账号。
- Provider 在迁移、Shadow 和切流前保持 disabled；旧运行和效果仅封存为不可重放历史，迁移不得创建 River job 或 EER effect。
- v2 `customer_id` 不是 v3 OneID。成员只能用源快照中 namespace 完整的 verified identity，通过 v3 Identity Port 解析为 canonical `customers.id`。
- 无命中、跨根命中、非法 scope 分别进入 `unresolved`、`conflict`、`invalid`；不建客、不绑身份、不自动合并。
- 源库存在 `enrolled`、`queued` 或 `outcome_unknown`，源凭据可写，manifest 漂移、计数等式不成立、目标没有指定的 active 管理员，立即停止。
- 加密快照和密钥均为 `0600`，不得进入 Git；数据库 URL 只从环境变量读取，不放在命令参数或日志中。

## 2. 只读盘点与冻结

先停止 v2 自动化运营写入口并完成在途效果对账，再使用只读账号：

```bash
export AICRM_V2_AUTOMATION_DATABASE_URL='<read-only source DSN>'
bin/migrate-automation-operations inspect \
  --source-system ai-crm-v2-production
```

盘点必须确认：schema allowlist 完整、`writable_credential=false`、active enrollment/action 和 `outcome_unknown` 均为零。该命令不输出外部身份和数据库 URL。

## 3. 加密快照

```bash
umask 077
bin/migrate-automation-operations keygen \
  --key-file /secure/aicrm-automation-operations.key
bin/migrate-automation-operations extract \
  --source-system ai-crm-v2-production \
  --snapshot-file /secure/aicrm-automation-operations.snapshot.enc \
  --key-file /secure/aicrm-automation-operations.key
bin/migrate-automation-operations validate \
  --snapshot-file /secure/aicrm-automation-operations.snapshot.enc \
  --key-file /secure/aicrm-automation-operations.key
```

快照使用 AES-256-GCM 鉴权加密，包含迁移所需身份值，因此只能在受控主机保存。输出文件已存在时命令拒绝覆盖。

## 4. 目标 dry-run 与导入

先对 v3 执行平台 migration，再选择一个 active 管理员 ID 作为迁移 actor。所有源 active 配置都会以 paused 导入。

```bash
export AICRM_DATABASE_URL='<target DSN>'
bin/migrate-automation-operations dry-run \
  --actor-id <active-admin-id> \
  --snapshot-file /secure/aicrm-automation-operations.snapshot.enc \
  --key-file /secure/aicrm-automation-operations.key

bin/migrate-automation-operations apply \
  --actor-id <active-admin-id> \
  --snapshot-file /secure/aicrm-automation-operations.snapshot.enc \
  --key-file /secure/aicrm-automation-operations.key \
  --confirm-import
```

每个 logical table 必须满足：

`source = imported + duplicate + mapped + unresolved + conflict + invalid + quarantine`

人工确认每个身份桶和发送人隔离桶后，使用同一加密快照做完整重放：

```bash
bin/migrate-automation-operations replay-check \
  --actor-id <active-admin-id> \
  --snapshot-file /secure/aicrm-automation-operations.snapshot.enc \
  --key-file /secure/aicrm-automation-operations.key
```

重放必须零新增且 `provider_effects_created=0`、`river_jobs_created=0`。

## 5. 对账与回退

apply 输出稳定 `batch_key`。用该键完成目标对账：

```bash
bin/migrate-automation-operations reconcile --batch-key <batch-key>
```

只有计数恒等式成立、导入事务前后 EER/River 计数相等，batch 才能进入 `reconciled`。历史运行不生成当前 Automation run/enrollment。

回退为非破坏性操作，只暂停导入的人群包并保留快照、source map、quarantine 和历史审计：

```bash
bin/migrate-automation-operations rollback \
  --batch-key <batch-key> \
  --confirm-rollback
```

任何已激活的导入包都会阻止回退；不得手工删除迁移证据。

## 6. Shadow 与切流前验收

- 使用原始加密快照执行可重复读 Shadow。命令只输出 source package ID、target package ID、计数和相等性，不输出身份值或 canonical customer ID：

```bash
bin/migrate-automation-operations shadow \
  --batch-key <batch-key> \
  --snapshot-file /secure/aicrm-automation-operations.snapshot.enc \
  --key-file /secure/aicrm-automation-operations.key
```

- `ready_for_probe=true` 才表示：batch 已 reconciled；配置、reference time、canonical member count/digest 全部相等；所有源成员均已唯一映射；导入包仍 paused/archived；导入未新增 EER/River；且导入包没有 `outcome_unknown`。
- v2 写入冻结后只能生成一次最终全量加密快照；禁止双主写。
- 逐包补齐或重建不兼容的 v2 定义，确认 Agent published digest、素材、sender eligibility 与生产策略后人工激活。
- Provider 探针必须使用单收件人、已授权固定话术和新幂等键；以 Provider receipt 与 EER reconciliation 为成功证据。

## 7. Provider 探针、限量放开与停止条件

迁移、Shadow 与业务预检期间必须保持：

```dotenv
AICRM_AUTOMATION_OPS_PROVIDER_MODE=disabled
AICRM_AUTOMATION_OPS_MAX_RECIPIENTS=1
```

完成操作人、固定话术和唯一收件人审批后，才可与全局 `AICRM_OUTBOUND_PROVIDER_ENABLED=true`、`AICRM_WECOM_ENABLED=true` 一起短时设置：

```dotenv
AICRM_AUTOMATION_OPS_PROVIDER_MODE=probe
AICRM_AUTOMATION_OPS_MAX_RECIPIENTS=1
AICRM_AUTOMATION_OPS_PROVIDER_PERMISSION=fixed-script-send-authorized
```

探针必须记录 run ID、recipient ID、effect ID、generation/fence、Provider receipt digest 和最终对账状态。`accepted`、`queued` 或 HTTP 200 均不构成成功。只在 `provider_accepted` 或 `delivery_proven` 且无 `outcome_unknown` 后，才能改为 `limited` 并设置已审批上限。

发现身份错配、成员摘要漂移、发送人不合格、内容版本漂移、Provider 证据缺失或任何 `outcome_unknown`，立即恢复 `disabled` 并停止扩量；未知效果只能原键查询、可信回调或带 generation/fence/evidence digest 的人工对账，禁止换键重试。
