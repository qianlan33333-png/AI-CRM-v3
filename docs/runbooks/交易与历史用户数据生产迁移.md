# 交易与历史用户数据生产迁移 Runbook

本轮以 `docs/prd/2026-09-05-v3-parity/00-control.md` 和 `11-deployment-pending.md` 为准：当前只完成开发、测试、PR与非生产集成，以下生产命令是下一阶段待办，不在本轮执行。两套系统独立存在，不停旧、不切流；本文件只覆盖 commerce 历史，不代替权益/优惠券和其他板块各自的导入对账。

## 1. 安全边界

- Provider 开关保持 disabled，历史终态不得创建 External Effect。
- 源库只读；目标写入只通过 `cmd/migrate-commerce-history` 和各领域 Port。
- 快照 `0600`、不入 Git；日志只输出行数、金额、digest 和安全错误码。
- 任何源覆盖缺失、manifest 漂移、OneID scope 未确认或对账不等时立即停止。

## 2. 全量快照

规范化文件必须使用 `aicrm-commerce-history-v3`，并包含六个为真的 coverage 位：identities、wechat_pay_orders、wechat_pay_refunds、wechat_shop_orders、wechat_shop_refunds、alipay_orders。

- `subjects[]` 是权威源用户主体，每个主体列出其 `identity_keys`；同一 identity 只能属于一个主体。
- `identities[]` 只接受 namespace 完整且来源可证明的 verified identity。
- 无法安全补全 scope 的源身份进入 `identity_quarantines[]`，仅保留 source key、原因码和 digest 等安全证据，禁止写 raw UnionID/OpenID/手机号。
- 订单同时引用 payer subject、payer identity 和 beneficiary subject；三者全空表示 floating 历史订单，禁止部分归属或猜测。

```bash
bin/migrate-commerce-history --mode=inspect --snapshot=/secure/commerce-v3.json
bin/migrate-commerce-history --mode=dry-run --snapshot=/secure/commerce-v3.json
sha256sum /secure/commerce-v3.json
```

`inspect` 可用于检查不完整快照；`dry-run` 和 `apply` 对任何缺失覆盖失败关闭。

### 2.1 仅验证微信支付历史订单

管理页 `/admin/orders` 提供受控的订单快照检查、导入和对账入口。它只接受 `wechat_pay_orders-only` manifest：除 `wechat_pay_orders` 外所有 coverage 必须为 false，身份、主体、隔离和退款数组必须为空，订单必须全部 floating。该入口不会创建 OneID、Payment/Refund 或 External Effect，不能作为全量 commerce 迁移完成凭证。

操作顺序固定为：选择同一个 JSON 文件 → 检查 SHA-256/摘要 → 勾选确认 → 导入生产 → 对账。只有超级管理员可执行；浏览器上传前必须再次核对目标域名、文件绝对路径、本次冻结文件的实际行数、金额与确认摘要。对账成功后刷新订单列表，确认 API/UI 的总数、金额和历史只读标识。

无法使用浏览器上传时，可由已授权的生产运维人员在目标主机上使用同一个窄化合约。CLI仅识别 `AICRM_DATABASE_URL` 或 `DATABASE_URL`，不支持 `AICRM_DATABASE_URL_FILE`。以下示例假设部署阶段已在受保护路径准备仅含一行DSN、以换行结束、权限0600的 `/secure/v3-database-url`，并先核对其为V3目标；文件及凭据尚未由本轮创建或复制。执行时关闭shell追踪，不回显值：

```bash
set +x
IFS= read -r AICRM_DATABASE_URL < /secure/v3-database-url
export AICRM_DATABASE_URL
```

所有以下 `apply/reconcile` 示例复用该受保护环境，完成后 `unset AICRM_DATABASE_URL`。`inspect/dry-run` 不需要连接目标数据库。

```bash
bin/migrate-commerce-history --order-only --mode=inspect --snapshot=/secure/orders.json
bin/migrate-commerce-history --order-only --mode=dry-run --snapshot=/secure/orders.json
bin/migrate-commerce-history --order-only --mode=apply --snapshot=/secure/orders.json --manifest-sha256=<confirmed-sha256> --confirm-apply
bin/migrate-commerce-history --order-only --mode=reconcile --snapshot=/secure/orders.json --manifest-sha256=<confirmed-sha256>
```

`--order-only` 必须与浏览器入口使用相同的 `ValidateOrderOnly`：只允许 floating 微信支付订单，拒绝身份、主体、退款或其他 Provider 覆盖，且对账必须确认全部订单 `effect_eligible=false`。

## 3. 导入

先做源备份和目标备份，记录 T0 水位。对已确认 digest 执行：

```bash
bin/migrate-commerce-history \
  --mode=apply \
  --snapshot=/secure/commerce-v3.json \
  --manifest-sha256=<confirmed-sha256> \
  --confirm-apply
```

同一 `run_key + manifest digest` 可安全重放；同 run key 的 digest/schema 漂移必须报冲突。每个源主体在一个 PostgreSQL UoW 内完成首身份显式 provision、其余身份附着和 append-only receipt；任何已存在跨根命中整笔回滚且不自动 merge。身份隔离行也有独立 receipt。订单和支付/退款分别走 Order、Payment Port。

## 4. 独立历史快照边界

1. 以只读一致性快照记录来源版本和 `(updated_at, source_pk)` 水位，冻结文件、覆盖范围及唯一run key；不关闭旧交易入口、不改旧回调。
2. 对同一冻结文件执行 inspect、dry-run，核对逐条结果后才在获准的生产阶段执行 apply、reconcile。
3. 同一run key不接收摘要漂移。旧环境在水位之后的变化不在该快照覆盖范围内，必须另列待处理事实；禁止假装追加delta会更新已导入历史终态。
4. V3运行时不得持续回读旧数据库或把历史导入变成双主写，Provider开关不会因历史导入成功自动启用。

## 5. 对账

```bash
bin/migrate-commerce-history \
  --mode=reconcile \
  --snapshot=/secure/commerce-v3.json \
  --manifest-sha256=<confirmed-sha256>
```

对账按当前 run 的 receipt 集合检查：每个 canonical subject 的全部身份可由 OneID 精确解析到同一 Customer；canonical subject 和 identity quarantine 回执数相等；输入数和完成数相等；订单、支付、退款笔数相等；订单金额和退款金额相等。成功后 run 才标记 `reconciled`。

随后按 Provider/状态/自然日抽样源库、manifest、v3 API 与管理页四点一致。任一不等时停止该批次后续操作，不启用 Provider，不改变两套系统各自的读取路由。

## 6. 上线与回退

- 唯一总集成候选获准后按现有流程合并部署一次。配置V3独立的支付凭据、回调域名与测试对象后，再按真实业务验收结果决定启用写入；不切换旧系统路由。
- `accepted/queued/executed` 不等于支付或退款成功；仅验证回调或主动查询可形成终态。
- 迁移回退不硬删审计、receipt 或冲突事实。已被 v3 新交易引用的根不得自动回滚。
- 出现身份错误归属、重复退款、Provider outcome unknown 被换键重试、权限绕过、PII 泄漏或静默丢行时立即关写并进入人工处置。
